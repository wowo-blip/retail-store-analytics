# 项目设计与工程取舍

## 业务问题

项目不把销售额等同于经营成果，而是按以下顺序分析：

1. 销售额扣除退货后，实际留下多少净收入；
2. 净收入是否集中在英国、少数国际市场或少数客户；
3. 客户复购和 cohort 活跃是否支持稳定关系；
4. 哪些商品和市场的退货信号值得进一步调查；
5. 这些结论受到哪些缺失数据、样本量和口径限制。

## 数据流

```text
UCI 官方 ZIP
  │ 下载 + 固定 SHA-256
  ▼
Online Retail II Excel（本地、不提交）
  │ 两个工作表读取 + 标准化 + 异常画像
  ▼
Zstandard Parquet（保留原始行定位与状态）
  ├──────────────► DuckDB 演示查询 ─► Streamlit
  │
  ▼
MySQL 事务批量导入 ─► 参数化 SQL ─► 报告 / Streamlit
  │
  └──────────────► pytest 跨后端对账 + Playwright
```

## 为什么保留而不是删除异常行

取消单、负数量、缺失客户 ID 和非正价格本身就是业务事实。项目将每一行分类为：

- `sale`：进入销售、订单和商品指标；
- `return`：以正的退货金额展示，同时在净收入中保留负号；
- `excluded`：不进入经营汇总，但仍保留在 Parquet 和 MySQL 中供审计。

这种设计避免“清洗后看不到发生过什么”，也允许质量报告与经营指标使用不同的分母。

## 为什么使用 Parquet + MySQL 双路径

MySQL 展示事务、权限隔离、索引和 SQL 指标能力，但在线托管 MySQL 会提高招聘者查看门槛。Parquet 经 Zstandard 压缩后约 12.8 MB，DuckDB 可以按需查询而无需把约 500 MB 的 Pandas 对象全部载入内存。

MySQL 是工程主链路，DuckDB 只承担演示后端。两者不是各算各的：测试逐表比较 KPI、月份、国家、商品、客户和 cohort 结果。

## 数据库设计

`fact_retail_lines` 保留：

- 稳定 `line_id`、工作表和源行号；
- 原始业务字段；
- `line_amount`、重复/取消/服务代码标记和 `transaction_type`；
- 源文件 SHA-256。

索引围绕看板访问路径设置：日期+国家、发票、客户+日期、商品+日期、交易类型+日期。看板账户只有 `SELECT`；ETL 账户拥有创建表和插入所需的最小权限。

百万行载入和最终对账位于同一数据库事务中。最终 SQL 或行数对账失败时，全量回滚，避免出现“看板能打开但数据库只导入一半”的状态。

## 可复现与交付

- 下载脚本只接受固定 UCI ZIP 哈希；上游文件变化必须显式审查。
- 原始 Excel 不提交，避免仓库膨胀；处理后 Parquet 带完整署名和许可说明。
- GitHub Actions 使用 MySQL 8.4 服务，重新下载、导入、生成报告并运行测试。
- 浏览器冒烟测试不是只检查 HTTP 200，而是真实等待 KPI、切换标签页并检查 Streamlit/页面错误。
- Docker Compose 通过健康检查和 `service_completed_successfully` 保证 MySQL → ETL → 看板启动顺序。

## 已知取舍

- MySQL 的百万行单事务导入约需数分钟，速度不如 `LOAD DATA INFILE`；当前优先保证权限边界和跨环境一致性。
- 商品描述可能随时间变化，商品聚合以标准化后的 `stock_code` 为主键，描述只用于展示。
- 客户 ID 缺失行保留收入但不能进入客户分析，因此财务总额和客户净收入总额不会完全相等。
- 当前 RFM 为分析期内相对分层；生产系统应持久化规则、监控漂移并通过实验验证触达策略。
