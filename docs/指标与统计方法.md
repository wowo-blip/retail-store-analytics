# 指标、SQL 与统计方法

## 统一口径

每一行是一笔样例交易，Invoice ID 唯一；不是客户唯一标识。SQL 中所有指标接受同一开始日期、结束日期、城市、客户类型和品类条件。日期两端均包含；空多选代表无记录，不自动解释为全选。

| 指标 | 定义 |
|---|---|
| 销售额 | SUM(total)，含源表税额；数据库保留四位小数，界面显示两位 |
| 交易笔数 | COUNT(*)；由唯一交易编号约束确保不会重复计数 |
| 商品件数 | SUM(quantity)，与交易笔数不同 |
| 平均交易金额 | SUM(total)/COUNT(*)，不是按城市均值再简单平均 |
| 日均销售额 | 销售额/筛选区间日历天数，不是营业日平均 |
| 平均评分 | 交易评分的算术平均 |
| 品类占比 | 品类金额/同一筛选范围销售额，SQL 窗口函数计算 |
| 门店排名 | 同一范围按销售额 DENSE_RANK 排序 |
| 7 日移动平均 | 当日及前6个日历日金额的均值；窗口不足7日不显示 |

仅有约3个月样本，3月未覆盖完整月份，不计算年度季节性、同比或完整月份环比增长。日报缺记录补0仅为了在样例时间轴上汇总，不声称真实营业额为0。

## SQL 的作用

`sql/metrics.sql` 包含七个查询：KPI、门店、每日、品类、城市×品类、月份、交易明细。聚合由 MySQL 执行；Pandas 负责绘图格式、描述统计和重抽样。所有值通过 SQLAlchemy 参数绑定，IN 条件使用 expanding 参数。
`sql/schema.sql` 定义事实表与导入元数据表，并建立交易主键、来源外键、日期/城市索引和品类/日期索引。

## 销售额差异的对称分解

令 N 为交易笔数、A 为平均交易金额、R=N×A。两店差异：

```text
R_A − R_B
= (N_A − N_B) × (A_A + A_B)/2
+ (A_A − A_B) × (N_A + N_B)/2
```

两项严格加总回销售额差异（允许数据库均值的小数舍入误差）。分别命名为交易笔数项与平均交易金额项。它是代数恒等式，不是可操控因素的因果贡献。

## 共同日期簇 Bootstrap

目标量是两店“总金额/交易笔数”的差，不是两组日均值的简单差。

1. 在当前范围内按日期×门店汇总金额与笔数。
2. 对从最早到最晚交易日期的日历日期重抽样，有放回地抽出相同数量的日期。
3. 同一次抽样对所有门店使用共同日期权重，保留同日交易及跨门店共同变化。
4. 每家店用加权金额之和除以加权笔数之和，计算两店差值。
5. 重复5000次，固定随机种子20260907，取2.5%与97.5%分位数作为95%区间。

每家门店至少30笔交易、14个有交易的日期；至少99%的重复抽样有可用分母，才输出区间。此阈值是项目中避免极端稀疏区间的实务规则，不保证区间覆盖率。

主分析假设日期簇之间近似独立。额外的7日循环移动块保留块内相邻日期，用作短期序列相关的敏感性检查；它仍需要序列有足够稳定性，不解决所有时间趋势问题。
逐对区间没有做多重比较校正。区间包含0不证明均值完全相等；区间不含0也不代表门店管理措施产生了因果效果。
重抽样应保留数据依赖单位的原则参考 [Stata 官方分组 Bootstrap 说明](https://www.stata.com/support/faqs/statistics/bootstrap-with-panel-data/)；本项目的日期分组选择由样例结构和上述假设决定，并非直接套用该页面的面板模型。

## 品类标准化与大额交易检查

统一品类权重均值：用合并筛选样本的各品类交易占比，给每店各品类均值加权。缺少品类时显示缺失，不用0冒充缺失均值。
去除最高1%交易：按当前合并样本统一第99百分位阈值，暂时排除高于该阈值的交易，再比较均值；不改数据库原始数据。
这两项只提供描述性敏感性分析，不将标准化结果称为已控制所有混杂。

## 质量与可复现性

原文件 SHA-256 存入导入元数据。所有校验通过后在一个事务内插入，再核对总笔数和 Decimal 金额。不使用 UPSERT 覆盖不同版本数据。重复运行同一文件先对账，返回 already_loaded。
上游 Excel 作为原始输入保留。报告中的数字来自 MySQL，没有手工编造展示数据。依赖完整版本在 requirements-lock.txt。
MySQL 实例隔离方式参考 [MySQL 官方多实例文档](https://dev.mysql.com/doc/refman/8.4/en/multiple-windows-servers.html)。
